# 人设与回复投递验收 · 2026-11-06

本记录覆盖人设配置到实际模型请求、回复筛选和微信通道投递之间的实现。改动已纳入 `0.2.0-preview.6`；真实模型的口吻表现与这里使用隔离模型、隔离回执的业务回归分别核对。

## 已复现的问题与修复

| 触发条件 | 原结果 | 修复 |
| --- | --- | --- |
| 模型已通过素材工具选好有效配文，但最后另写一段客服套话 | 先改写不会发送的正文，改写失败会阻止整个图片回复 | 在已完成模型回合中先确定真正的待发送正文，再净化、限长和改写；仍然检查模型完成状态 |
| 素材配文需要改写，主模型回合期间默认模型、全局身份或生成设置发生变化 | 通道单独改写配文时重新读取设置，混入下一轮配置 | 配文在原 runner 回合内完成一次改写，沿用已捕获的人设、身份、账号要求、模型和参数 |
| 工具选择仅发送图片，或未采用的模型正文超过文字上限 | 无用正文可能触发改写或长度错误 | 空配文保持空；长度检查针对真正待发送的内容，不凭空补正文 |
| 配文包含明确的思考标记 | 原配文直接经过通道，缺少普通正文所用的公开内容过滤 | 配文与普通文字共用公开文本过滤，显式思考内容不会进入投递正文 |
| 代码、译文、引文或第三人称说明中出现“AI 助手”等词 | 被当成主动自我说明，可能反复改写并最终拒绝发送 | 跳过代码内容，保留所需译文与引用，仅检查非引用正文中实际的自我说明 |
| 配置为“不要客服套话，回复使用标题和编号” | 前半句的否定词让整句格式要求失效 | 按独立子句识别正向格式要求，保留相邻的否定约束 |
| 请求“给我三个方案”“分点说明”或英文 steps/options/poem | 所需编号和作品标题可能被当成普通闲聊的机械格式 | 识别明确枚举、分步及中英文常用格式请求，保留作品和有效内容 |
| 自定义全局身份要求“只写诗歌、每次追加签名”，同时进行记忆提取、压缩或图片理解 | 聊天呈现要求被拼入内部任务，可能破坏 JSON 或客观笔记约定 | 后端提供的记忆、摘要和视觉任务使用各自输出约定；普通回复、到期 Agent 和二次改写继续继承身份 |
| 当前请求说“别给我行动清单”，人设默认编号或请求中同时出现正反要求 | “清单”关键词被当成结构许可，违规列表无需改写就返回 | 先核对显式禁止，再应用默认许可；有序/无序列表、标题和加粗分别跟随最后一条明确方向，引用与代码不当作格式指令 |
| 全局身份明确固定签名，同时请求简短介绍并切换到另一会话人设 | 后置的人设与自然规则可能让模型省略固定要求 | 管理员全局身份放在最终约束位置，明确人设名字/语气与固定要求同时满足；普通生成与二次改写保持一致 |

素材选择回调只决定文字内容，不发送消息，不修改素材授权。生成完成后仍核对当前账号、授权、连接及素材启用状态，发送结果继续以服务端回执为准。旧 runner 没有实现文字选择回调时，保持已有配文兼容流程。

内部任务隔离要求后端同时提供明确的任务模式与专用输出约定；普通聊天正文写入 `mode` 或 `systemOverride` 不会改变身份、工具权限或任务类型。

修复前运行 `node --test tests/persona-delivery.test.mjs tests/reply-style.test.mjs`：16 项中 10 项通过、6 项失败，已复现上述配文与误判问题。首批统一构建后，人设、投递、作品、会话设置、保存取消和昵称触发共 84 项通过，记录为 `storage/logs/persona-audit-checkpoint1.tap`。

补充内部任务隔离与明确枚举请求后，再次统一构建；当时全量 Node 回归 **337 / 337 通过**，包括全部新增业务用例。已核对 `storage/logs/full-audit-node.tap` 中的实际执行结果；没有通过删除失败断言或仅检查非空输出来替代验证。最终发布回归为 **345 / 345 通过**，详见总验收记录。

首轮真实 DSH 模型已完成 25 个场景，自动检查 24 项通过、1 项未通过；真实跨会话回复遗漏了管理员固定签名。18 套人设的逐套原句、风格差异与不足见 [真实模型审阅](PERSONA-MODEL-REVIEW-2026-11-06.md)，没有把回复非空当作所有口吻验收通过。

真实素材工具的配文及仅图场景使用隔离传输回执，实际微信消息和群通知均为 0；这些测试不证明生产微信端已经真实收到图片。
