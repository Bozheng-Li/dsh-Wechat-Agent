## 1. 结论与范围

本项目已经具有一个业务 harness：微信消息准入、任务与会话归属、DSH 调用、按需工具、状态持久化、发送回执、取消与恢复均有实际实现。下一步收益最大的方向是让这些能力共享明确、可测试的契约，并建立从真实用户任务到最终外部结果的评估闭环。

建议继续以 DSH 承担原生 Agent、Session、模型适配、沙箱及工具执行；插件负责微信账号与会话权限、业务任务、记忆资料、外部写入确认和产品界面。优先改进证据、恢复、预算、可观测性与测试，不建议直接替换宿主或叠加第二个完整 Agent 循环。

这里区分两种 harness：

- **运行 harness**：生产中让模型持续执行的系统，包括上下文、工具、状态、恢复和权限。
- **评估 harness**：隔离环境、输入场景、可控故障、评分器和证据报告。它必须走足够接近生产的调用链，才能评价运行 harness。

DSH、Codex 和 Pi 是可复用运行时；LangGraph 主要提供状态与工作流编排基础设施；MCP 是工具与资源互操作协议；Anthropic 的工程文章提供设计和评估方法。它们解决的问题不同，不能按“谁功能多”直接替换。

## 4. 主流方案的关键经验

### 4.1 DSH：复用原生会话，业务控制面保持清楚

DSH 官方 SDK server 文档 [S1] 将 JSON-RPC server 描述为薄适配层：模型、Agent、持久化和工具由组合树提供；每个 `sessionId` 对应 Agent/Session；事件与状态变化向外流出。文档特别区分 prompt 接收确认、会话事件与最终等待完成，并指出超时不是回滚，不能自动重试有副作用的命令。

**适合本项目的应用**：

1. 用一个明确的 `DshRuntimeAdapter` 汇集公共 API 能力探测、会话创建/恢复、事件投影、取消和释放，减少宿主版本知识散在 runner 中。
2. 保持真实用户原话、DSH 原生任务历史与微信侧业务任务关联。微信会话摘要不应覆盖原生工作历史；恢复失败不应偷偷新建空会话。
3. 明确三个状态：提交被接受、执行完成、微信投递确认。页面和最终回复分别展示，禁止从 `whenIdle` 或“有最终文字”推断外部动作已成功。
4. 对借用桌面会话、同一会话并发输入和 preset 局部服务建立原生 SDK 回归；验证释放插件工具不会移除原生工具，也不会干扰其他 Agent。

**取舍**：先针对实际 rc.5 安装验证。只有出现明确兼容需求才采用公网 master 新方法；不能为了追新直接改为未证明可用的 SDK 面。

### 4.2 Anthropic 长任务：交接工件、明确验收、逐项验证

早期长任务研究 [S2] 用初始化阶段建立完整功能列表和工作记录，后续 Agent 增量推进并通过端到端操作验证。文章直接描述两种失败：只完成一部分就宣布结束，以及单元测试通过但用户操作仍不可用。其价值在于把目标与证据留在可持久读取的工件中。

更新研究 [S3] 又展示 planner/generator/evaluator 分工、独立评价与按组件消融；模型能力变强后，作者移除了原先有用的 sprint 结构，部分任务中也不再需要额外 evaluator。文中实验是特定编码场景，不能推导为所有微信请求都需要三个 Agent。

**本项目应做**：工作任务保存用户要求、明确交付物、可执行验收、已证实事实、待办项、当前实际状态和证据引用。需要跨长时段/多次续接时才生成结构化交接。验收优先检查文件可打开、内容满足要求、工具真实结果和投递 ACK；“模型说完成”只是一段输出。

**不宜照搬**：强制每轮重置上下文、对每个简短聊天都加规划/评审、无限自动“再试一次”。这些会增加延迟、成本和重复外部动作风险。每个额外模型步骤必须以独立样本上的净收益证明其价值。

### 4.3 上下文工程：按需读取、分层预算、保留关键关系

Anthropic 上下文研究 [S4] 推荐高信号上下文、最小但足够的工具集合、just-in-time 读取、适当预载的混合策略，以及压缩、结构化笔记和子任务隔离。它也指出运行期检索会增加延迟，过度压缩可能删除后续才重要的信息。

**本项目的下一步**：

- 给 system、最近对话、角色资料、历史参考、工具 schema、工具结果和图片各自记录预算及超限处理，最后再校验总预算。配置单位明确区分字符与真实 tokenizer tokens。
- 工具先返回短目录、范围、时间、来源与可继续读取的 handle/cursor；正文按需读取。工具结果不应成为绕过历史预算的通道。
- 压缩保留尚未完成的用户约定、人物主体、否定/更正、时间与单位、原始证据引用、未知投递结果；不要把不确定事实压缩成确定事实。
- 角色记忆保存来源和时间范围；检索先限定账号/会话/发起人，再排序。对同名人、引用里的第三人、旧事实被新事实否定进行独立测试。
- 记忆删除与事实纠正需要让索引、摘要、缓存和延迟任务同时尊重版本或代次，不能仅删除一个展示条目。

**验收**：在长历史、图片、跨页检索和多轮更正中同时报告 grounding、召回、未授权泄露、请求体积与 p95 延迟。仅减少 prompt 字符数不能证明回答更好。

### 4.4 工具设计与 MCP：结构清楚、响应有界、授权由应用实施

工具设计研究 [S5] 强调避免重叠工具、清楚命名与参数、返回有用而节省 tokens 的信息，并用任务级 eval 改进工具。MCP 注解说明 [S9] 明确 readOnly/destructive/idempotent/openWorld 都是提示；不能依赖声明本身证明操作安全或幂等。

本项目可先在内部 registry 增加统一元数据：`effectKind`、`scope`、`timeoutClass`、`retryPolicy`、输入/输出 schema 版本、结果字节预算、是否支持取消、是否需要持久动作键。权限检查、幂等与回执仍由后端真正执行，不能交给模型自行遵守。

当前 `wechat_capabilities` 的按会话延迟注册属于 **DSH 内部工具呈现**。若未来暴露为 MCP 服务，需要单独设计协议适配：本次核对的 `2026-07-28` 规范要求工具列表不能因连接状态或其他请求副作用而变化，允许按请求携带的授权变化，并建议稳定排序 [S11]。不能直接把“调用 load 后 tools/list 多一组”的内部实现宣称为新版 MCP 合规服务。

MCP 结构化结果与模型 structured output 也不同：前者是工具服务生产的结果数据，后者是模型生成约束。未来外接时按实际协商版本验证 `outputSchema`、`structuredContent` 和缓存元数据；保留对旧客户端的兼容，不因为新版规范允许数组/原始值就立即更改现有返回合同 [S11–S12]。

### 4.5 LangGraph：持久化边界不等于外部 exactly-once

LangGraph 的当前 Functional API 文档 [S6] 明确：恢复是从 checkpoint 边界重放，不是回到中断的同一代码行；已完成 task 可复用保存结果，但开始后未完成的 task 仍可能再次执行。副作用、随机数和时钟读取应有明确 task 边界；写操作需幂等键或查询已有结果。

Checkpointer 文档 [S7] 区分 `sync`、`async`、`exit` 持久化：更强耐久性需要在继续执行前等待写入，异步或退出才写入会存在崩溃窗口。其依据适用于本项目的设计思考，并不证明任意框架能把微信写入变成 exactly-once。

**本项目应保留并加强**：发送前持久记录动作身份和内容哈希；取得真实确认后再保存完成；未明确确认的结果保留 unknown，走只读对账或已有 Owner 恢复流程。把自动重试限制在明确无外部副作用或确有幂等保证的步骤。

**何时考虑引入 LangGraph**：将来确有大量多阶段长流程、人工中断、分支回放、可视化编排，且自有状态机维护成本已有证据时，选一个离线取材/文稿审批工作流试点。先定义存储唯一归属和边界，再引入。当前直接把聊天、任务、朋友圈三套状态迁入第二个 runtime，收益尚无本项目证据。

### 4.6 Codex：应用拥有业务事实，harness 拥有 Agent 执行

官方 Codex 平台文章 [S8] 区分脚本入口、SDK 和 app-server：产品集成常需持续线程、事件、工具和审批；应用继续拥有业务上下文、记录及控制。它支持本项目当前“业务插件 + 原生执行器”的边界设计。

可借鉴 thread/turn/item 级事件标识与生命周期接口，设计宿主适配契约和统一运行记录。若未来增加 Codex 执行后端，应作为明确的可选适配器，独立核验权限、模型访问、恢复、附件与用户交互，不假定 DSH Agent 与 Codex thread 状态可直接互换。当前没有更换宿主的用户要求或收益证据。

### 4.7 Pi：保持小核心，用扩展承担具体业务

Pi 官方 README [S10] 定位为 minimal、extensible harness，提供交互、JSON/print、RPC 和 TypeScript SDK，并刻意不内建某些诸如子 Agent 和 plan mode 的工作流。

对本项目最有价值的是组织原则：稳定的模型/工具/会话核心，业务能力按显式接口扩展；不让所有场景都经过复杂规划链。可以给聊天、工作、视觉、记忆提取、朋友圈审核定义不同的最小能力面，并测量是否真的减少请求成本和选择错误。

不建议仅因“轻量”而替换 DSH。微信项目已经依赖 DSH 原生模型服务、桌面会话、沙箱与公共事件，更换会带来协议、存储、工具和 UI 的迁移成本。

## 6. 评估 harness 的落地方法

### 6.1 先保留已有实验的优点

`PROMPT-PROGRESSIVE-V12-2026-11-10.md` 记录 18 个场景、每题每版本重复两次、三版本合计 108 次任务；固定模型、隔离会话、候选顺序平衡、bundle 与模板冻结，以及隐去版本的独立 AI 评审。该历史报告已区分核心事实、整段正确、自然度和服务失败，值得沿用。这里没有重新运行它，也不把旧分数当成本次当前源码的实测成绩。

下一轮需扩大场景而不是只围绕已见题修提示：按实际功能和失效模式建立矩阵，在样本冻结后评估。保留开发集、回归集、未见质量集；一条真实故障可成为回归用例，但不能继续称作未见题。

### 6.2 四层证据，分别给结论

| 层级 | 应证明的内容 | 不足以证明的内容 |
| --- | --- | --- |
| L1：纯逻辑/状态单元测试 | 数据合同、边界、转换、权限与错误处理 | 真实宿主、页面或微信可用 |
| L2：本地系统集成 | 真实存储/RPC/调度/进程/字节处理，传输及模型受控 | 提供方输出质量及微信服务器行为 |
| L3：真实 DSH SDK 与界面 | 宿主 API、注册、工具、续接、事件，以及真实页面交互 | 真实模型一定选对工具；真实微信外部写入已确认 |
| L4：受控真实链路 | 指定测试账号、目标与模型下，从输入到最终外部事实的结果 | 其他账号、模型、规模和时序下的普遍可靠性 |

每个功能都记录达到哪层；缺少条件写“未验证”，不能把 skip 或模拟 ACK 算作微信实测。真实外部写入仅在明确测试目标与授权范围内执行；本次研究不发送微信消息。

### 6.3 场景设计必须包含相反案例

根据 Anthropic eval 方法 [S13]，测试“应该触发”也要测试“不应触发”，否则容易优化出所有问题都搜索、所有回复都读记忆、所有模糊句都启动工作的问题。

- 聊天/工作分流：明确委托、闲聊讨论、否定、不确定、引用命令、简短确认、多个发起人的不同旧任务。
- 搜索：时效与专业查证、用户禁止联网、纯创作、私人资料、公开主题提炼、空结果、限流、认证错误、备用失败、来源互相冲突。
- 记忆：已有事实、无记录、已删除、当前更正、多人物、群聊转述、跨页尾部答案、损坏或读取失败。
- 外部动作：成功、拒绝、请求前取消、请求后未知、部分成功、重复事件、迟到 ACK、账号切换、重启与权限撤回。
- 长任务：成果存在但不可打开、文件哈希变化、文件产生却未登记、执行完成但未回传、恢复到同一真实会话、原会话被其他输入占用。
- UI：主流程、保存失败、重复点击、窄屏、键盘、加载中切换账号、离开后返回、两处编辑同一 revision。

### 6.4 评分器与报告

先用确定性评分检查作用域、文件、持久记录、ACK、时间和数量；再对无法完全编码的自然度、事实依据、要求完整性使用明确 rubric 的独立评审，并保留人工校准入口。不要仅因回答出现“已完成”“已搜索”就通过。

至少输出：任务首次交付成功率、整段有依据比例、应调用/不应调用工具的准确率、跨重复试验一致性、重复副作用数量、未知状态误报数量、p50/p95 延迟、真实 usage 与缺失 usage 的比例、每个成功任务成本。字符数不换算成虚构精确 tokens 或费用。

`pass@k` 是 k 次中至少一次成功，`pass^k` 是 k 次全部成功 [S13]。微信交互更看重稳定交付；不能用重试很多次后挑一个成功样本证明可靠。报告保留全部尝试，包括提供方错误；内容质量可另用共同有效样本，但要同时呈现总体交付分母。

建议首轮设置的门槛是：权限越界、重复副作用、未知被标成功的确定性用例为零失败；主要功能回归全通过；质量指标不退化，再看延迟和成本改善。这里的“零失败”只是该测试集门禁，不是对生产零风险的保证。对主观评分和性能的容忍度，应在运行候选前冻结，避免看见结果后改阈值。

## 7. 推荐实施顺序与停止条件

1. **先建立可信基线**：H01、H02、H14、L1–L3 场景矩阵。先修实际失败与错误指标，再比较模型效果。退出条件：每个主要功能都有可重现命令、明确层级和结果。
2. **保障业务动作**：H03–H06、H11、H18。以故障注入覆盖投递、朋友圈、提醒和取消，不同时重构所有存储。退出条件：各中断点恢复满足既有不变量。
3. **提升答案与检索**：H08–H13、H17。逐项实验正文提取、结果预算、记忆时效、按需评审。每轮保留一个未变基线，避免把工具、提示、模型和预算一起改后无法归因。
4. **扩展长期能力**：H15–H16、H19–H22。先做真实长任务与容量基准；只有达到瓶颈或有明确新场景才考虑 LangGraph、数据库或第二个 runtime。

停止或回退候选的条件：权限/防重不变量失败、真实交付下降、效果只出现在已见题、额外调用成本超过收益，或需要依赖目标宿主未证实的 API。回退应恢复代码/模板候选，不逆向覆盖已产生的真实回执与用户数据。
