## 1. 结论、执行范围与计数口径

本轮原版 18 个专项入口为 **15 通过、3 失败**：17 项队列首轮为 14 通过、3 失败，另行补跑手动记忆压缩通过。管理员和工作区失败来自旧文案、旧折叠区选择器；隔离副本适配已确认的界面契约后，两条流程均继续到底并通过。自动安排原版两次在同一处失败，等待界面完成刷新后通过；受控请求实验另外证实了保存过程中新草稿被旧提交覆盖的产品缺陷。

默认 UI 原版在记忆标签键盘导航处失败，六标签适配后完整流程通过。视觉全量发现一个布局缺陷，在五种宽度、两种主题上表现为十个文档纵向溢出实例；独立 DOM 样式消融确认了隐藏 legend 的定位包含块问题。

本轮使用 `storage/cache/electron-40.9.3/electron.exe` 隐藏窗口，专项最多两路并发，各轮使用独立状态、浏览器 profile 和输出目录。前端 React、localhost RPC、StateStore 与相关业务服务为实际实现；账号、联系人、模型响应、微信传输和 ACK 为合成夹具。通过的 `fixture-summary.json` 明确记录真实微信消息和真实模型请求均为 0。失败轮次依据同一隔离架构运行，不能把合成 ACK 写成真实微信验收。

因此，本轮证明的是实际页面经本地 RPC 到业务服务的隔离集成行为。它不覆盖真实 DSH 外壳加载、宿主插件权限、真实微信连接、模型输出质量、实际社交操作成功率或长期在线稳定性。

## 5. 自动安排：原版时序失败与确定性草稿丢失分开归因

### 5.1 原版删除后改频率失败

原版两次均是：删除未来自动计划 → 夹具确认后端计划已删除 → 输入每天 3 条 → 点击保存 → 等待 16 秒后后端仍不为 3。失败截图显示输入 2、保存按钮禁用，浏览器 `errors` 为空。

只加观测的版本与显式等待 UI settled 的版本通过，因此这一失败具有时序敏感性；后端写入完成并不代表页面 mutation 后的 reload、busy 与受控输入状态全部完成。当前证据尚不足以把两次原版失败精确归因成“删除请求必然吞掉编辑”。观测版通过也不能反证不存在问题。

观测通过轮次的关键 Unix 毫秒时间保存在 `ui-arrangement-observe/{rpc-audit.jsonl,ui-observations.json}`：删除请求 `1794364077448`、响应 `1794364077455`；输入 3 `1794364077473`；change 后 dirty/可保存 `1794364077475`；点击 `1794364077481`；configure 请求 3 `1794364077490`、响应 `1794364077500`；清 dirty `1794364077511`。这些是一次通过样本，不是失败的因果轨迹。

### 5.2 受控实验确认保存期间的新编辑丢失（总报告 F12）

隔离 launcher 仅扩展既有 `holdNext/heldRequest/releaseRequest` 白名单，允许暂停 `moments.plans.delete` 与 `moments.publishing.configure`；真实页面和业务实现均不变。测试不是对禁用 DOM 强行赋值：原 `input` helper 等待可见、未禁用、非只读、允许指针事件的控件，并触发正常 input/change。每个关键阶段另记下 `editable/busy/dirty/saveDisabled/value/persisted`。

| 阶段 | 页面值 | 已保存值 | 输入可编辑 | busy | dirty | 保存按钮 |
| --- | ---: | ---: | --- | --- | --- | --- |
| 暂停删除请求，输入 3 | 3 | 2 | 是 | 是 | 是 | 禁用 |
| 释放删除、等待刷新结束 | 3 | 2 | 是 | 否 | 是 | 可用 |
| 提交 3 并暂停保存请求，再输入 4 | 4 | 2 | 是 | 是 | 是 | 禁用 |
| 释放旧保存、等待刷新结束 | **3** | 3 | 是 | 否 | **否** | **禁用** |

最后一行违反“完成旧提交不能丢弃较新的可编辑草稿”的断言，实际失败为 `'3' !== '4'`。删除期间编辑的对照通过，保存期间编辑的对照失败。关键阶段和失败均保存在 `ui-arrangement-controlled/{controlled-draft.json,report.json}`，另有 `ui-observations.json`、`rpc-audit.jsonl`、`final-state.json` 与 `arrangement-controlled-after-save.png`。

原因链：`frontend/pages/moments/arrangement-fields.jsx` 的数字/时间/文本输入未随 busy 禁用；`frontend/pages/moments/publishing-page.jsx:95` 在 `await state.execute(...)` 后无条件 `setGlobalDirty(false)`；`:41` 的 effect 随后用已保存设置同步 global。该保存提交的是 3，却把提交后输入的 4 一并标成干净并覆盖。不能据此推断其他所有表单都存在相同问题，需要按相同状态机检查。

建议 P1：给草稿引入编辑代次或提交快照。保存完成只更新持久基线；只有当前草稿仍等于提交快照时才清 dirty。存在较新编辑时保留 4 及可保存状态，并允许下一次提交。若选择保存时锁表单，需要统一所有可编辑控件，并明确产品体验；本轮更推荐保留编辑能力与 revision 契约。回归必须覆盖旧保存成功/失败、删除刷新、轮询、账号/页面切换和较新编辑，不能只增加固定 sleep。

## 6. 点赞评论页纵向溢出的根因（总报告 F11）

原版 visual 十个错误均为 `Document vertical overflow outside workspace`。视口和 document clientHeight 均为 942，document scrollHeight 在宽度 1280/768/430/375/320 下分别为 1068/1260/1597/1703/1752，明暗主题相同。它是一个缺陷的十个实例，不是十种独立布局错误，也不是十项对比度错误。

独立探针读取 DOM 并做局部 CSS 消融：`frontend/styles/interactions.mjs:40` 将 `.wa-interaction-setup legend` 绝对定位隐藏，但其 fieldset 没有建立定位包含块，legend 的 `offsetParent` 是 BODY。320px 时手动表单 legend 的底边为 1752.49，与文档高度 1752 对齐，视觉隐藏节点仍撑高根文档。

仅在隔离 DOM 注入 `.wa-panel .wa-interaction-setup fieldset { position: relative !important; }` 后，五宽度 × 两主题的 document scrollHeight 全部回到 942；workspace scrollHeight 保持原值 1944/2077/2700/2828/2876。仅给自动表单定位不能解决手动表单的问题；隐藏手动 legend 或让整个 workspace 定位也能消除症状，但前者伤害无障碍语义，后者影响范围更大。

建议 P2：给具体 fieldset 建立定位包含块，保留 legend 语义。正式修复后需回归可见/隐藏内容、焦点滚动、键盘导航、窄屏、明暗主题和 document/workspace 两级尺寸。DOM 消融只是根因证据，没有替代原版 full visual 的失败结果。探针的 `report.json`、`adaptation.json` 和截图位于 `memory/overflow-probe/`；源文件与原驱动事后哈希保持不变。
