# 记忆体系

[返回总架构](01-总架构.md)

## 分层与归属

记忆模块位于 `modules/memory/`，包含会话窗口、长期事实、图片、人物卡与检索。窗口、原始事实和图片仍以账号与来源会话定界；人物卡以 `accountId + personId` 唯一标识，在同一账号的私聊、群聊和朋友圈中共享。人物卡共享不扩大图片、工作文件或其他工具权限。

| 层 | 核心文件 | 内容与用途 |
| --- | --- | --- |
| 会话窗口 | `conversation/store.mjs`、`compaction.mjs` | 独立 `memory.json`，近期条目、摘要、压缩前归档；不改写原始消息档案 |
| 长期事实 | `long-term/store.mjs`、`roles/*.mjs` | `global-memory.md` 保存来源明确的事实/全局备注，侧车 JSON 记录来源游标和提取状态 |
| 图片记忆 | `images/store.mjs`、`generated.mjs`、`references.mjs` | 保存原图/索引，区分 `conversation` 与 `generated` 集合，核验哈希与引用 |
| 查询 | `query/tool.mjs`、`work-tool.mjs` | 按词相关性检索历史或用 `wechat_memory` 按需读取；工作模式只按允许的快照查询 |
| 人物卡 | `roles/maintenance.mjs`、`profile-extraction.mjs`、`tool.mjs` | 独立后台 Agent 自动整理；`wechat_role_card` 提供共享读取、搜索和异步更新 |
| 管理 | `actions.mjs`、`backend/storage/role-cards.mjs` | Owner RPC：查看、编辑、压缩、清空、角色卡、图片导入/删除 |

## 一次聊天如何用记忆

接收消息后 `StateStore` 将真实观察内容写入会话档案，再由 `ConversationMemory.append` 更新窗口，并将 incoming 原话加入人物整理队列。新会话首条消息即使由历史初始化导入，也必须触发这条回调。人物卡不进入助手人设；回复只预载少量人物索引及相关字段，更多信息通过渐进能力目录中的 `wechat_role_card` 读取。工具的 update 只排队，不直接采信模型提交的新事实。

`PersonMemoryMaintenance` 使用独立队列和独立 DSH Agent 会话，不进入聊天 drain。`roleCardSettings` 全局配置默认开启，普通更新默认每人 20 条，也可改为按时间（默认 60 分钟）；首次建卡遵守所选频率。消息、设置、重新上线唤醒调度，最近到期的一次性定时器负责延迟任务，一小时扫描补漏；空队列不调用模型。明确纠正或 Agent 冲突请求可提前触发，但遵守总开关；Owner 页面手动整理可在自动关闭时执行。

最多并发 2 人，同一人只运行一个更新。`backend/storage/role-card-schedule.mjs` 保存本轮来源快照、待处理消息的累计起点和下一次到期时间；大段来源可继续分批，执行中新增的普通消息重新累计。切换设置后重新计算计划并取消旧自动任务，不暂停聊天；队列、来源、重试和字段证据随卡片落盘。启动后分批扫描保留的聊天，群成员无需先拥有私聊。模型提交字段补丁后，宿主验证人物、逐字引文、来源代次与版本；新版本、撤权、换账号、清空来源和取消都会阻止旧结果写入。全局设置通过 `memory.role.settings/configure` 读取和保存，按 revision 防止陈旧页面覆盖新设置。

`memory-maintenance.mjs` 空闲时安排压缩及长期提取；失败保留原文和待处理状态，不以摘要覆盖聊天档案。`roles/extraction.mjs` 验证提取来源，`reflection.mjs` 仅在风险触发时复核回复。图片引用、生成图记忆在发出前都需要重新验证仍存在且未被清空/删除。

## 保存与删除语义

`storage/memory/index.json` 记录会话索引与窗口设置，会话文件按账号哈希/会话目录保存。长期 Markdown 是正文权威来源；旧事实保留来源元数据。生成图与聊天图片分开存放，删除标记及清空代次不混用；工作任务历史扫描不能把已明确清空的图重新导入。`config.yaml` 保存记忆窗口、保留期和图片开关；各层记录在其独立目录中。
