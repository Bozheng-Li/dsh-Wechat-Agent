## 边界与进程

`backend/wechat/worker-client.mjs` 在插件宿主侧用 `spawn(process.execPath, ['lib/worker.cjs', root], {stdio:['ignore','ignore','ignore','ipc']})` 启动子进程，提供 `call(op,args,{signal,timeoutMs})`、`send`、`media`、`readMoments` 等接口。它维护递增请求 ID、等待表与状态快照，并转发 `message`/`status` 事件。Worker 退出会拒绝未完成请求；发送类请求在断连时标记结果可能未知。

`backend/worker.mjs` 是构建入口，实际运行逻辑在 `backend/wechat/worker.mjs`：创建 `ProtocolBackend`、`QrLoginManager`、存储保护与操作分发。`runtime/native_login_worker.py`、`runtime/native_engine.py` 和 `runtime/wechat39-engine/` 为受平台限制的微信登录资源，只有 Windows x64 完整包才具备实际登录能力。

## IPC 消息契约

| 方向 | 类型 | 含义 |
| --- | --- | --- |
| 宿主→Worker | `call` | 带 `id/op/args` 的请求：连接、扫码、联系人、群成员、发送、图片和朋友圈读写 |
| 宿主→Worker | `cancel` | 请求取消；Worker 中写入/媒体操作使用 AbortController |
| Worker→宿主 | `ready` / `status` | 子进程就绪与在线账号快照 |
| Worker→宿主 | `message` | 协议观察到的微信消息，进入 `WechatChannel.receive` |
| Worker→宿主 | `result` | 请求结果或经过裁剪的公开错误 |

在 Worker 内再次检查当前真实登录账号与 `args.accountId` 相同；朋友圈按 `scopeKey` 限制实际发起人上下文。敏感协议参数不作为普通 RPC 结果透出。不同读取操作各有超时，发送与朋友圈写入以真实结果/回执决定最终状态。

## 协议实现

`backend/wechat/protocol/backend.ts` 管理会话、长连接、心跳、同步、联系人与发送队列；`transport.ts` 负责传输，`wire.ts` 负责编码/解码，`session.ts` 管理认证。`login.ts` 组织扫码。`image-download.ts`、`media-loader.mjs` 从观察到的资源标识读取微信图片，避免把未解析媒体冒充已理解内容；`file-upload.ts` 与 `media.ts` 处理发送格式。

朋友圈协议拆分为读取（`moments.ts`、`moments-user-page.ts`、`moments-images.ts`）、写入（`moments-write.ts`）和可见范围（`moments-audience.ts`）。引用消息在 `reference.ts` 对接统一的 `shared/message-references.mjs` 契约。

## 发送一致性

聊天侧先持久化 `sending` 意图，再调用 `WorkerClient.send(...)`（内部通过 IPC 的 `send` 操作交给 Worker）。只有服务端明确确认的消息 ID 被上层认定为 `sent`；多文件成果需逐项比对名称、字节数、哈希和消息 ID。超时、取消或 IPC 断开不等于微信未送达，相关记录保持 `unknown`/`partial` 供人工核对，不能自动重试。
